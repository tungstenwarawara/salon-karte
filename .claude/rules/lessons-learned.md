  - 対策: `get_owned_salon_ids()` を SECURITY DEFINER で作成し、staff の RLS から salons を直接クエリせずにこの関数経由にする

## カラム名・クエリ整合性
- `.select("description")` → 正しくは `memo`。ビルドでは検出不可（文字列型） (2026-02-21)
- `.select("total_price, skin_condition")` → 別テーブルのカラム名を誤指定。Supabaseは空配列を返すだけ (2026-02-21)
- 全クエリに `.eq("salon_id", salon.id)` 欠落 → ルールに明記済みだったが守られず (2026-02-21)
- `treatment_menus` に `.order("sort_order")`（同カラムは appointment_menus 等にのみ存在）→ PostgRESTがエラーを返し `data` が null → `menus ?? []` で空配列になり、Web予約の変更画面でメニューが1件も選べない状態が続いた。顧客の問い合わせで発覚 (2026-08-11)
  - チェックスクリプトが `.select()` しか見ていなかったのが原因 → `.order()` / `.eq()` / `.in()` 等、カラム名を文字列で渡す全メソッドを照合対象に拡張済み
  - `data ?? []` のフォールバックは「取得0件」と「クエリ失敗」を区別できない。空になった原因を握りつぶす点に注意
  - 同じ穴が `.insert()` / `.update()` / `.upsert()` にも残っていたため、渡すオブジェクトのキーも照合対象に拡張済み (2026-08-11)
- **対策**: `python3 scripts/check-select-columns.py` をコミット前に必ず実行

## 非同期処理（Vercel サーバーレス）

> **警告**: レスポンス返却後に await されない Promise は**完了しない**。ローカル `next dev` では
> プロセスが生き続けるため必ず成功し、**本番でしか再現しない**。テストでも型チェックでも検出不可能。

- Web予約の顧客向け確認メールが届かない (2026-08-14)
  - 原因: `sendWebBookingNotifications({...}).catch(() => {})` と fire-and-forget した直後に
    `NextResponse.json()` を返していた。Vercel はレスポンス送出後に関数インスタンスを凍結するため、
    送信中の Promise が中断される
  - 症状の出方が分かりにくい:
    - 予約作成 → メール送信までが**毎回5〜6分遅延**していた（凍結されたインスタンスが
      次のリクエストで解凍されたときに再開されるため）
    - 4件中2件で顧客メールだけが消失（オーナー向けは届く）。「たまに届かない」ため
      迷惑メール判定や受信側の問題と誤認しやすい
    - Resend の送信ログに**そもそも記録が残らない**ので、bounce/spam との切り分けが必要
  - 対策: `import { after } from "next/server"` でバックグラウンド処理を包む。
    booking の submit / change / cancel の3ルートに適用済み
  - 併せて実施: メール送信を並列（`Promise.allSettled`）から**逐次**に変更。
    Resend の既定レート制限は 2リクエスト/秒で、同時送信は 429 で消える危険がある。
    顧客向けメールを必ず先頭に置くこと（変更・キャンセルURLは顧客向けメールにしか載らない）
  - **新しく API ルートで通知・ログ送信を追加するときは、必ず `after()` で包むか `await` する**

## 課金・Webhook

> **警告**: 課金系の不具合は「静かに」壊れる。ユーザーは金を払っているので気づくが、
> こちらのログにもテストにも何も出ない。Stripe ダッシュボードを見に行くまで分からない。

- 冪等性マーカーを**処理前に**書き、その後の DB 更新失敗を握りつぶして 200 を返していた (2026-08-16)
  - Stripe は 200 を受け取ると再送しない。さらにマーカーが残るため**手動リプレイも「処理済み」で弾かれる**
  - 結果、「課金されたのに plan_type が free のまま」が**恒久固定**される。回復手段がゼロになる
  - 対策: DB 更新の失敗は必ず throw → マーカーを削除 → 500 を返して Stripe に再送させる
  - **`console.error` + `break`/`return` で 200 を返すのは、外部システムからの通知では常に間違い**
- 冪等でない外部API（Stripe の `createBalanceTransaction` 等）を呼ぶ処理は throw させてはいけない (2026-08-16)
  - 再送で二重付与される。失敗は記録に留め、次回のイベントで再試行させる
  - 「throw して再送させる」と「throw せず記録に留める」の使い分けは**その処理が冪等かどうか**で決まる
- 重複ガードを自前DBの状態（`plan_type`）だけで判定していた (2026-08-16)
  - その状態が立つのは Webhook 受信後なので、決済直後の数秒間はガードが効かない
  - 二重契約が成立すると、`salon_id` でupsertする実装では**旧契約が追跡不能のまま課金され続ける**
  - 対策: 外部システムの状態は**外部システムに聞く**（Stripe API で契約中サブスクを確認）
- 決済完了画面が自前DBを1回読むだけだった (2026-08-16)
  - Stripe は決済直後にリダイレクトするが、DB 反映は Webhook 受信後。
    支払い済みの画面に「おためしプラン ¥0/月」「アップグレード」ボタンが並ぶ状態が発生しうる
  - 誤解を招くだけでなく、**再課金ボタンを押させて二重契約を誘発する**
  - 対策: 反映をポーリングし、待機中と失敗時は課金を促すUIを一切出さない
- `cancel_at_period_end` を保持していなかった (2026-08-16)
  - Stripe の期間末解約は `status='active'` のまま。保持しないと「次回請求日」を出し続け、
    解約したお客様から手続きの成否が判別できない
- `event.created` を `new Date(x * 1000).toISOString()` に直接通していた (2026-08-16)
  - 値が欠けると RangeError → 通知という**副次的な処理のために課金反映まで失敗**し再送ループに入る
  - 表示・通知のためだけのデータで本処理を落とさない
- 実績のない書き方を、失敗時の影響が大きい経路に入れない (2026-08-16)
  - UPDATE の返り値に対する PostgREST の埋め込み取得（`.select("salon_id, salons(name)")`）を
    支払い失敗の処理に入れかけた。リポジトリ内に前例がなく実行検証もできていなかった
  - 検証できないなら、実績のある書き方に落とす

### 検証方法の教訓
- 本番イベントの「再送」で検証できるのは重複ガードだけ。**修正した失敗経路は素通りする** (2026-08-16)
- 外部サービスをモックしたユニットテストなら、本番に触れずに失敗経路まで固定できる
- **テストを書いたら、必ず一度わざと壊して落ちることを確認する**（ミューテーション確認）。
  通るだけのテストは、何も保証していない可能性がある
