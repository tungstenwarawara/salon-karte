# セットアップフロー簡素化 — デザイン原則に基づく全体再設計

> 作成日: 2026-03-24
> 目的: 業界標準のUXデザイン原則に基づいて、salon-karteの導線・フロー・オンボーディングを統一的に再設計する
> ステータス: 検討中（実装前）

---

## 参照したデザインガイドライン

| ソース | 核となる教え |
|--------|------------|
| **Apple HIG** | 最高のオンボーディングは「オンボーディングがないこと」。設定は前提条件ではなく最適化 |
| **Google Material Design** | オンボーディングは3モデル（Self-Select / Quickstart / Top User Benefits）から選ぶ |
| **NNGroup** | ウォークスルー型チュートリアルはタスク遂行を改善しない。文脈に合った支援が有効 |
| **SaaS業界調査** | Time-to-Value（価値到達時間）が最重要指標。60秒で自信を持てたユーザーは自分で探索する |

---

## 5つの設計原則（salon-karteに適用）

調査結果を統合し、salon-karteに適用すべき5つの原則を定義する。
**全ての改修はこの原則に照らして判断する。**

### 原則1: 価値到達を最速にする（Time-to-Value）

> サインアップから「最初の成功体験」までの時間を最小化する

- salon-karteの「Aha! moment」= **最初のカルテを記録できた瞬間**
- サインアップ → カルテ記録までの間にある全障壁を除去または最小化
- 現状の障壁: サロン名入力 → 営業時間(任意) → メニュー登録(任意だがないと詰む) → ダッシュボード → 顧客登録 → カルテ作成
- 目標: サインアップから5分以内にカルテ記録完了

### 原則2: 空状態を教育面にする（Empty States as Onboarding）

> 空のページは「壊れている」のではなく「始まりの招待」

- 全てのデータ一覧ページの空状態が、次にやるべきことを明確に伝える
- 空状態のCTAが、依存関係も含めて解決する（例: カルテ一覧の空状態 → メニュー未登録ならメニュー登録に先に誘導）
- Apple HIG: 「空状態はオンボーディングの変装」

### 原則3: 文脈に沿って段階的に開示する（Progressive Disclosure）

> 全機能を最初に見せない。ユーザーが必要とする瞬間に開示する

- 初回は3つだけ: 顧客登録、メニュー登録、カルテ記録
- Web予約、LINE連携、在庫管理、分析は「その機能のページに初めて来たとき」に説明
- 設定項目は「必須」と「あとで」を明確に区別
- Apple HIG: 「遅延できるものは全て遅延する」

### 原則4: 設定は前提条件ではなく最適化（Defaults over Configuration）

> デフォルト値で動作し、カスタマイズは後からでよい

- 営業時間: デフォルト(月-土 10:00-20:00)で即動作、カスタマイズは任意
- 予約ルール: デフォルト(当日OK、制限なし)で即動作
- メニュー: プリセットで即動作、カスタマイズは任意
- 「設定しないと使えない」を「設定すればもっと便利に」に変える

### 原則5: 行動で学ぶ（Learn by Doing）

> チュートリアルではなく、実際の操作を通じて学ぶ

- ウォークスルーツアーやスライドショーは不要（NNGroup: 効果なし）
- 代わりに、チェックリストの各項目が「実際にやること」と直結
- 各ステップに所要時間を表示（「2分」→ 心理的ハードル低下）
- 成功時にトーストで肯定フィードバック

## 現状とのギャップ分析

| 原則 | 現状 | ギャップ | 重大度 |
|------|------|---------|--------|
| 1. 価値到達最速 | メニュー未登録でダッシュボードに到達 → カルテ作成不可 | **致命的** — Aha momentに到達できない | 高 |
| 2. 空状態が教育面 | 空状態CTAは存在するが、依存関係の解決を案内しない | **中** — 「カルテを登録する→」を押してもメニューがないと失敗 | 中 |
| 3. 段階的開示 | 設定ページが19ページ一覧で並ぶ、優先順位なし | **中** — 情報過多で何から手をつけるかわからない | 中 |
| 4. デフォルトで動作 | 営業時間・予約ルールはデフォルトあり。メニューだけデフォルトなし | **高** — 唯一のハード依存にデフォルトがない | 高 |
| 5. 行動で学ぶ | チェックリスト6項目あり（良い）。ただし所要時間表示なし | **低** — 基本構造は良好、改善余地あり | 低 |

## 改修計画（原則に基づく統一的アプローチ）

### Phase 1: 価値到達の障壁除去（原則1+4）

**目標: サインアップ → 最初のカルテ記録を5分以内に**

#### 1-a. セットアップウィザードに「業種選択 + プリセットメニュー」を追加

```
現在のウィザード:
  Step 1: サロン名（必須）
  Step 2: 営業時間（スキップ可）
  Step 3: メニュー登録（スキップ可 → 問題の根源）
  Step 4: 完了

提案:
  Step 1: サロン名（必須）
  Step 2: 業種選択（エステ/ネイル/まつエク/リラクゼーション/その他）
         → 選択した業種のプリセットメニュー3-5件を提案
         → 「このまま登録」or「カスタマイズして登録」or「あとで自分で登録」
  Step 3: 完了（営業時間はデフォルト適用、設定から変更可能と案内）
```

**変更点:**
- ウィザードを4ステップ → 3ステップに削減（営業時間ステップを削除、デフォルト適用）
- 業種選択でメニュープリセットを提案（原則4: デフォルトで動作）
- 「あとで」を選んでも、カルテ/予約作成時にインラインで作成可能（1-b で対応）

**リスク:** 低 — DB変更なし、既存ユーザー影響なし（ウィザードは初回のみ）

#### 1-b. メニューのインライン作成（依存関係の解消）

カルテ作成(`records/new`)と予約作成(`appointments/new`)に、メニューが0件のときインライン作成UIを追加。

```
メニューが0件の場合:
  ┌──────────────────────────────────┐
  │ 施術メニューがまだ登録されていません  │
  │                                  │
  │ メニュー名: [           ]        │
  │ 施術時間:   [  60  ] 分         │
  │ 料金:      [  5000 ] 円         │
  │                                  │
  │        [メニューを登録して続ける]   │
  │                                  │
  │ または 設定→メニュー管理で登録 →    │
  └──────────────────────────────────┘
```

**設計根拠:** 物販記録の「商品から選ぶ / 自由入力」パターンと同じ。salon-karte内に前例がある。

**リスク:** 低 — UIの追加のみ、DB変更なし

---

### Phase 2: 空状態の全面改善（原則2+5）

**目標: どのページに来ても「次に何をすべきか」が明確**

#### 2-a. 依存関係を認識する空状態

現在の空状態は「Xはまだありません。最初のXを登録する→」だが、
依存関係が未解決のケースを考慮していない。

```
カルテ一覧が空 + メニューが0件の場合:
  現在: 「最初のカルテを登録する →」→ 遷移先でメニューがなくて詰む
  提案: 「カルテを記録するには、まず施術メニューの登録が必要です」
        [メニューを登録する（3分）→]

カルテ一覧が空 + メニューがある + 顧客が0件の場合:
  提案: 「カルテを記録するには、まずお客様の登録が必要です」
        [お客様を登録する（2分）→]

カルテ一覧が空 + メニューあり + 顧客ありの場合:
  提案: 「最初のカルテを記録する（3分）→」
```

**変更箇所:**
- `records/page.tsx` の空状態（メニュー/顧客の存在チェック追加）
- `appointments/page.tsx` の空状態（同上）
- Web予約ページの空状態（営業時間チェック追加）

**リスク:** 低 — 表示ロジックの追加のみ

#### 2-b. チェックリストに所要時間を追加

```
現在:
  □ 営業時間を設定する
  □ 施術メニューを登録する
  □ 最初のお客様を登録する

提案:
  □ 施術メニューを登録する（3分）
  □ 最初のお客様を登録する（2分）
  □ 最初のカルテを記録する（3分）
  □ 営業時間を確認する（1分）← 「設定する」→「確認する」に変更（デフォルトで設定済みのため）
```

**変更点:**
- 所要時間を表示（心理的ハードル低下）
- 順序をJTBD（Jobs-to-Be-Done）に合わせて並べ替え
- Phase 1のフェーズ順に表示
- 「予約を入れてみる」は Phase 2 チェックリストのままでOK（段階的開示）

**リスク:** 低 — 表示の変更のみ

---

### Phase 3: 設定画面の再構成（原則3）

**目標: 設定を「必須」「推奨」「応用」に層別化し、段階的に開示する**

#### 3-a. 設定ハブのグループ再編

```
現在（19ページ、フラットに羅列）:
  サロン情報 / 営業時間 / 臨時休業 / メニュー / 予約ルール / Web予約 /
  カウンセリング / LINE連携 / スタッフ / シフト / データ取込 / データ出力 / プラン

提案（3階層に整理）:

  ━━ はじめに設定 ━━
  ・サロン情報（名前/電話/住所）
  ・メニュー管理
  ・営業時間

  ━━ 予約を受け付ける ━━
  ・予約/営業設定（営業時間 + 臨時休業 + 予約ルール + Web予約を統合）
  ・カウンセリングシート

  ━━ もっと便利に ━━
  ・LINE連携
  ・スタッフ/シフト管理
  ・データ取込/出力

  ━━ アカウント ━━
  ・プラン/お支払い
```

**変更点:**
- 設定ハブのグルーピングとラベルを変更（ページ数は Phase 3-b で削減）
- 「はじめに設定」グループにバッジ表示（未完了の場合）

**リスク:** 低 — 設定ハブの表示変更のみ

#### 3-b. 予約関連設定の統合（4ページ → 1ページ）

営業時間 + 臨時休業 + 予約ルール + Web予約 → 1ページ、セクション分け

```tsx
// /settings/booking/page.tsx (新規)
<PageHeader breadcrumbs={[...]} />

<Section title="営業時間">
  <BusinessHoursEditor />  // 既存コンポーネント流用
</Section>

<Section title="臨時休業・時間変更">
  <HolidayEditor />  // 既存コンポーネント流用
</Section>

<Section title="予約受付ルール">
  <BookingRulesEditor />  // 既存コンポーネント流用
</Section>

<Section title="Web予約">
  <WebBookingEditor />  // 既存コンポーネント流用
</Section>
```

**変更点:**
- 4つのページを1つに統合
- 各セクションは既存コンポーネントをそのまま使用
- 旧URLからリダイレクト設定

**リスク:** 中 — テスト範囲が広い、URLブックマーク問題

### Phase 4: 継続的オンボーディング（原則3+5）— 将来検討

#### 4-a. 各機能の初回訪問ガイド（Everboarding）

LINE連携、在庫管理、分析レポート等の応用機能は、**ユーザーが初めてそのページを訪れたとき**に簡単な説明を表示。

```
初回訪問時:
  ┌──────────────────────────────────────┐
  │ 📊 分析ダッシュボード                   │
  │                                      │
  │ カルテと売上のデータから、               │
  │ お客様の傾向や人気メニューを分析します。    │
  │                                      │
  │ カルテが10件以上記録されると、            │
  │ より精度の高い分析が表示されます。         │
  │                                      │
  │              [はじめる]                │
  └──────────────────────────────────────┘
```

**リスク:** 低 — 表示のみ、localStorageで表示済みフラグ管理

#### 4-b. サンプルデータ体験モード

サインアップ直後に「サンプルデータで体験する」オプション。
3顧客 + 3メニュー + 5カルテを自動生成 → ダッシュボードが「実際に使っている状態」で表示。

**リスク:** 中 — サンプルデータのクリーンアップ設計が必要

## 実施優先度と影響範囲

| Phase | 内容 | DB変更 | 影響範囲 | 工数 |
|-------|------|--------|---------|------|
| **1** | ウィザード改善 + インラインメニュー作成 | なし | setup, records/new, appointments/new | 小-中 |
| **2** | 空状態改善 + チェックリスト改善 | なし | records, appointments, dashboard | 小 |
| **3** | 設定ハブ再編 + 予約設定統合 | なし | settings/* | 中 |
| **4** | 初回訪問ガイド + サンプルデータ | なし | 各機能ページ | 中-大 |

**全Phase通じてDB変更なし** — これが最も重要。データモデルは健全なので触らない。

## 原則への適合チェック（改修ごとに確認）

改修を行う際、以下の5問に全て「はい」で答えられることを確認:

1. **この変更は、ユーザーが価値に到達するまでの時間を短縮するか？**
2. **データがない状態でも、次にやるべきことが明確か？**
3. **この機能は、ユーザーが必要とする瞬間に表示されるか？（早すぎないか？）**
4. **デフォルト値で動作するか？ 設定は必須ではなく最適化か？**
5. **ユーザーは説明を読まなくても、操作を通じて学べるか？**

---

## 変更しないもの

1. データモデル（テーブル構造、正規化、RLS）
2. 決済方法4種（cash/credit/ticket/service）
3. カルテ作成画面の一体型設計（施術+物販+回数券）
4. 回数券の管理方式
5. マルチテナント分離の仕組み
