> 更新日: 2026-04-28
> 目的: サロンオーナー（ユーザー）が「どの画面で何をすると何が起きるか」を**漏れなく**把握できるマニュアル。同時に、ドッグフーディング・人力テスト・E2E テストの基準としても使う。

| 観点 | このドキュメント | `user-flow-diagrams.md`（既存） |

## 対象読者

1. **サロンオーナー（ユーザー）**: 操作に困ったときに該当ファイルを開けば手順が書いてある状態
2. **テスター**: 各操作・条件分岐に対して期待動作が明示されている → 不具合検出の基準として使える
3. **開発者・Claude**: 仕様確定済みの動作を変更しないための回帰防止リファレンス

### スクショの差し込み

各画面の冒頭に `![画面名](./screenshots/{ファイル名}.png)` を**先に書いておく**。画像ファイルは Phase 2 で Playwright スクリプトで一括生成する。今は画像が無くてもマークダウンとしては有効。

### スクショファイルの命名規則

```
{ファイル番号 2桁}-{領域名}-{画面名}[-{状態}].png
```

| 例 | 説明 |
|----|------|
| `04-customers-list.png` | 顧客一覧 通常状態 |
| `04-customers-list-empty.png` | 顧客一覧 空状態 |

### 撮影想定環境

| 項目 | 値 |
|------|-----|

### 「実装済み」と「今後の予定」の書き分け

| 表記 | 意味 |
|------|-----|
| そのまま記述 | 実装済み・現行動作 |
| `> 注意:` | 実装済みだが分かりにくい挙動・落とし穴 |
| `> 今後の予定:` | 未実装。Phase 2 以降で対応予定 |
| `> 既知の問題:` | バグ・テスターから報告された不具合 |

## 操作と結果の記法ルール

### 「操作」の書き方

- **クリック**: 「`保存する` ボタンを押す」
- **入力**: 「メールアドレス欄に `〜` と入力する」
- **選択**: 「婚姻状況のドロップダウンで `既婚` を選ぶ」
- **遷移**: 「`+ 顧客を登録` を押す」（結果は「結果」列に）

### 「結果」の書き方

| パターン | 書き方の例 |
|---------|----------|
| 画面遷移 | `/customers/{id}` に遷移する |
| Toast 通知 | 画面上部に「顧客を登録しました」と表示される |
| エラー表示 | 画面上部に赤い ErrorAlert で「登録に失敗しました: {実際のエラーメッセージ}」と表示される |
| 状態変化 | ボタンが `保存中...` に変わり、押せなくなる |
| データ変化 | DB の `customers` テーブルに 1 行追加される |

## バリデーションの書き方

```markdown
| 項目 | 必須 | 形式 | エラー時の挙動 |
| --- | --- | --- | --- |
| 姓 | ✅ | 文字列 | HTML5 `required` で「このフィールドを入力してください」 |
| 電話番号 | ❌ | 任意の文字列（書式チェックなし） | — |
| 身長 (cm) | ❌ | 数値（小数1位まで） | parseFloat で NaN なら null として保存 |
```

## メンテナンス方針

1. 実装変更があったら、該当ファイルを更新する
2. スクショは UI 変更時に Playwright スクリプトで再生成（Phase 2 以降）
3. 「今後の予定」の項目は実装完了次第「実装済み」に書き換える
4. 各ファイルの冒頭に `更新日` を入れる。古い記述は信用しない方針

> **静的な進捗表は記載しない**（陳腐化するため）。各ファイルは「現時点のスナップショット」として、必要に応じて実測で再確認する。

## 次セッション開始の手順（Claude 向け）

このセクションは次回セッションで Claude が即着手できるための手順書。

### 1. このファイルの「ファイル一覧と進捗」表を確認

⬜ のファイルが残仕事。優先度高い順に量産する。

### 2. 既存の完成ファイルを参考にしてフォーマットを揃える

| ファイル | 用途 |
|---------|-----|
| `04-customers.md` | 各画面の操作・状態・バリデーションを書くフォーマットの基準 |
| `18-emails.md` / `19-line-messages.md` | 横断仕様（送信トリガー一覧）のフォーマット基準 |
| `20-cron-jobs.md` | バックエンド処理（人間の操作なし）の仕様の基準 |

### 3. 量産の進め方

各ファイルは次の手順で書く（中断リスクを抑えるため）:

1. **骨格を Write で作る**（タイトル + 各節の見出し + `（執筆中: SECTION-XXX）` プレースホルダー）
2. **各節を Edit で順次埋める**（1節ずつ、応答サイズを抑える）
3. 全節埋まったら**コミット & プッシュ**
4. このファイルの進捗表を ✅ に更新

### 4. ファイル作成前に必読

- 対応するソースコード（`src/app/.../page.tsx` 等）を Read
- 関連コンポーネント（`src/components/`）を Read
- 関連 API ルート（`src/app/api/`）を Read
- 該当領域の DB スキーマ（`src/types/database.ts` で型確認）

### 5. スクショは生成しない（Phase 2 で Playwright 自動生成）

`![名前](./screenshots/{番号}-{画面}-{状態}.png)` 形式のプレースホルダーは書く。画像ファイル本体は生成しない。命名規則は本ファイルの「スクショファイルの命名規則」セクション参照。

### 6. 完了後に進捗表を更新

このファイル（`00-overview.md`）の「ファイル一覧と進捗」表で、完成したファイルの状態を ⬜ → ✅ に更新し、行数を記入する。
