## 共通仕様（送信元・スキップ条件・失敗時挙動）

### 送信元アドレス

- 既定: `サロンカルテ <support@salonkarte.com>`
- 環境変数 `EMAIL_FROM` で上書き可能
- 全メール共通（サインアップ・予約系・リマインド全て同じ送信元）

### メール送信のスキップ条件

| 条件 | 挙動 |
| --- | --- |
| `RESEND_API_KEY` 環境変数が未設定 | メール送信を**スキップ**（コンソール警告のみ）。アプリの動作は止めない |
| 顧客の `customers.email` が null | 該当顧客向けメールはスキップ。オーナー向けは送信される |
| サロンの `salon.email` が null（オーナー向けのみ） | オーナー向けメールはスキップ |

> 設計思想: メールはオプショナル機能として扱う。Resend が落ちていても予約・カルテ操作は止まらない (graceful degradation)。

### 送信失敗時の挙動

| トリガー | 失敗時の処理 |
| --- | --- |
| 全トリガー共通 | `console.error` でログ出力 + Sentry に `feature` タグ付きで送信 |
| 予約確認メール（顧客向け）失敗時 | 予約自体は成功扱い。エラーは Sentry に記録 |
| 前日リマインド失敗時 | `stats.email.failed++` で集計。次回 cron 実行時に再送はしない（一度限り） |
| サインアップ確認メール失敗時 | サインアップは成功扱い。ユーザーは「確認メール再送」ボタンで再試行可能 |

### メールテンプレートの共通レイアウト

- 背景色: `#f5f1ed`（ベージュ）
- カード背景: 白、角丸 16px、最大幅 480px
- フォント: `'Hiragino Sans', 'Noto Sans JP', sans-serif`
- フッター: 「このメールはサロンカルテから自動送信されています」
- アクセントカラー: `#c4956a`（CTA ボタン）

### 配信ログ

- メール送信の成功・失敗ログは **DB には保存していない**（LINE は `line_message_logs` に保存している）
- Resend ダッシュボードの送信履歴のみが配信ログ
- Sentry にはエラーのみ記録

## トリガー詳細

### 1. サインアップ確認メール

**送信タイミング**: 新規ユーザーが `/signup` でアカウント作成を完了した直後

**送信先**: 登録時に入力されたメールアドレス（1通のみ）

**件名**: `【サロンカルテ】メールアドレスの確認`

**本文の主要内容**:
- 「サロンカルテへようこそ」の見出し
- 「メールアドレスを確認する」ボタン → `confirmUrl`（Supabase 発行）に遷移
- ボタンが押せない場合用に URL のテキスト併記
- 「このリンクは24時間有効です。心当たりのない場合は無視してください」

**リンクの有効期限**: 24時間（Supabase Auth 側の制御）

**スキップ条件**:
- `RESEND_API_KEY` 未設定 → スキップ（ユーザーには「確認メール再送」を案内するUIが必要だが現状は不明な状態になる）

**失敗時の挙動**:
- サインアップ自体は成功
- ユーザーがログインしようとすると Supabase が「メール未確認」エラーを返す
- ユーザーが手動で「確認メール再送」を要求できる（次節）

### 2. サインアップ確認メール 再送

**送信タイミング**: ユーザーがログイン画面の「確認メールを再送する」を押したとき

**送信先**: 入力されたメールアドレス（既存ユーザーであれば再送、未登録なら何もしない）

**件名・本文**: トリガー1と同じ

**セキュリティ配慮**:
- 該当アドレスが未登録でもエラーは返さない（メールアドレスの存在確認を防ぐ）
- レート制限あり（連続送信を防ぐ。Supabase 側の制御）

**スキップ条件**: トリガー1と同じ

### 3. 予約確認（顧客向け）

**送信タイミング**: 顧客が `/book/{salonSlug}` で予約完了したとき

**送信先**: 予約時に入力された顧客メールアドレス

**件名**: `【{サロン名}】ご予約を受け付けました`

**本文の主要内容**:
- 「ご予約を受け付けました」の見出し
- `{顧客名}様` 宛の挨拶
- 予約内容ボックス: 日時 + 所要時間 + メニュー
- アクションボタン:
  - `cancel_token` がある場合: 「予約を変更する」「キャンセルする」のリンク
  - ない場合: サロン電話番号の案内
- サロン名の署名

**スキップ条件**:
- `customers.email` が空 → スキップ
- `RESEND_API_KEY` 未設定 → スキップ

**送信失敗時**: 予約自体は成功扱い。Sentry に記録

### 4. 予約通知（オーナー向け）

**送信タイミング**: 顧客が Web 予約完了したとき（顧客向けと同時送信）

**送信先**: サロンの登録メールアドレス（`salons.email`）

**件名**: `【Web予約】{顧客名}様（{予約日時}）`

**本文の主要内容**:
- 「Web予約が入りました」の見出し
- お客様情報ブロック: 顧客名 + 新規/既存バッジ + 電話 + メール
- 予約内容ブロック: 日時 + メニュー + 所要時間
- メモ（顧客が入力した場合のみ）
- 「サロンカルテのダッシュボードで詳細を確認できます」の案内

**新規/既存の判定**: 該当顧客が初めての来店か（`appointments` の件数で判定）

**スキップ条件**:
- `salons.email` が空 → スキップ
- `RESEND_API_KEY` 未設定 → スキップ

### 5. 予約変更完了（顧客向け）

**送信タイミング**: 顧客が予約変更URL（`/book/change/{token}`）から日時/メニューを変更したとき

**送信先**: 顧客のメールアドレス

**件名**: `【{サロン名}】予約を変更しました`

**本文の主要内容**:
- 「予約を変更しました」の見出し
- 変更前: 旧日時（取り消し線で表示）
- ↓ アロー
- 変更後: 新日時 + 新メニュー + 所要時間
- サロン名の署名

**スキップ条件**:
- `customers.email` が空 → スキップ
- `RESEND_API_KEY` 未設定 → スキップ

**注意**: 予約変更は `cancel_token` を使う公開APIなので、誰でも token を知っていれば変更できる。ブルートフォース対策として token は十分な長さの URL-safe 文字列。

### 6. 予約変更通知（オーナー向け）

**送信タイミング**: 顧客が予約変更URLから変更したとき（顧客向けと同時送信）

**送信先**: サロンの登録メールアドレス

**件名**: `【変更】{顧客名}様（{新日時}）`

**本文の主要内容**:
- 「予約が変更されました」の見出し
- 顧客名
- 変更前: 旧日時 + 旧メニュー（取り消し線）
- 変更後: 新日時 + 新メニュー（太字強調）
- 「サロンカルテのダッシュボードで詳細を確認できます」

**スキップ条件**: トリガー4と同じ

### 7. 予約キャンセル完了（顧客向け）

**送信タイミング**: 顧客が予約キャンセルURL（`/book/cancel/{token}`）からキャンセルしたとき

**送信先**: 顧客のメールアドレス

**件名**: `【{サロン名}】予約をキャンセルしました`

**本文の主要内容**:
- 「予約をキャンセルしました」の見出し
- キャンセル済み予約の詳細: 日時 + メニュー
- 「再度予約する」ボタン（Web 予約 URL がある場合）
- サロン名の署名

**スキップ条件**: トリガー3と同じ

### 8. 予約キャンセル通知（オーナー向け）

**送信タイミング**: 顧客が予約キャンセルURLからキャンセルしたとき（顧客向けと同時送信）

**送信先**: サロンの登録メールアドレス

**件名**: `【キャンセル】{顧客名}様（{日時}）`

**本文の主要内容**:
- 「予約がキャンセルされました」の見出し（赤色）
- 「お客様がWeb予約をキャンセルしました」
- キャンセル内容: 顧客名 + 日時 + メニュー
- 「サロンカルテのダッシュボードで詳細を確認できます」

**スキップ条件**: トリガー4と同じ

### 9. 前日リマインド（顧客向け）

**送信タイミング**: 毎日 21:00 JST（`0 12 * * *` UTC）に Vercel Cron が `/api/cron/line-reminders` を呼び出す。LINE と**並行して**メールも送信

**送信先**: 翌日（日本時間）に予約があり、`status = 'scheduled'` の顧客全員（`customers.email` 登録済みのみ）

**件名**: `【{サロン名}】明日のご予約のお知らせ`

**本文の主要内容**:
- 「明日のご予約のお知らせ」の見出し
- 顧客名宛の挨拶
- 予約内容: 日時 + メニュー
- 変更/キャンセルリンク（cancel_token がある場合のみ）
- サロン名の署名

**LINE と同時送信**:
- LINE 友だち登録済み + `lineConfig.is_active && reminder_enabled` なら LINE も送信
- メールと LINE は**両方独立に**送信される（LINE で届いてもメールも届く）

**Cron 認証**:
- `Authorization: Bearer {CRON_SECRET}` ヘッダーが必須
- 検証失敗時は 401 エラー（メール送信されない）

**集計結果のレスポンス**:
```json
{
  "line": { "sent": N, "failed": N },
  "email": { "sent": N, "failed": N },
  "date": "YYYY-MM-DD"
}
```

**スキップ条件**:
- `customers.email` が空 → メールスキップ（LINE は別判定）
- `RESEND_API_KEY` 未設定 → メールスキップ
- 翌日の `status = 'scheduled'` の予約がない → そもそも cron が早期 return

> **既知の問題**: テスターから「LINE リマインドが届かない」報告あり。詳細は `19-line-messages.md` の「テスター指摘の切り分け」を参照。メール側は別経路だが、同じ cron で発火する。

## 迷惑メール対策の現状

### 実施済み対策

- ✅ Resend ドメイン認証（SPF / DKIM / DMARC）→ 緑チェック確認済み（2026-04-28）
- ✅ 送信元: 独自ドメイン `support@salonkarte.com`（Gmail 等の無料ドメインからの送信ではない）
- ✅ HTML テンプレートのテーブルレイアウト（Gmail 互換）
- ✅ プレーンテキスト URL の併記（ボタンが押せない場合用）

### 未実施・検討中の対策

| 対策 | 効果 | 工数 |
|------|-----|-----|
| Gmail Postmaster Tools にドメイン登録 | 送信ドメインの**評判（reputation）**を可視化、Gmail 側からの判定理由を確認できる | 小 |
| DMARC ポリシーを `p=quarantine` 以上に強化 | スプーフィング判定が厳しくなり、正規メールの信頼性向上 | 小 |
| `List-Unsubscribe` ヘッダー追加 | Gmail がスパム判定する確率を下げる | 中（テンプレート修正） |
| `mail-tester.com` で本文スパムスコア測定 | 10点満点で具体的な改善点が見える | 小（一回の測定） |
| 本文の販促語・絵文字の削減 | スパムフィルタを通りやすくなる | 小 |
| 確認メールに「サロンカルテ」と署名を含める | ブランド認識でスパム判定を下げる | 既に実施済み |
| 専用 Inbox プレビュー（Litmus 等） | 主要メールクライアントでの表示確認 | 中（外部サービス契約） |

### テスター環境で迷惑メール行きが起きている根本原因の仮説

DNS 緑チェック OK でも迷惑メール行きする場合、考えられる原因:

1. **新規ドメインのレピュテーション低**: salonkarte.com のドメイン評価が Gmail にまだ蓄積されていない（送信実績が少ない）
2. **DMARC が `p=none`**: 認証は通るが、ポリシーがゆるい
3. **`List-Unsubscribe` ヘッダー欠如**: Gmail はマーケティング系メールでこれを重視
4. **本文のリンク密度**: アクションボタン + フォールバック URL でリンクが多い（特に変更・キャンセル両方あるとき）
5. **テスター固有の設定**: そのテスターの Gmail フィルタ・フィードバックが影響

## テスター指摘の切り分け手順

### 「メールが届かない」報告を受けたときの確認順序

1. **そもそも送信されたか**
   - Resend ダッシュボード → Logs → 該当時刻の送信履歴を確認
   - 送信ステータス（delivered / bounced / complained / failed）を確認

2. **送信されているのに届かない場合**
   - 受信者の **迷惑メールフォルダ**を確認してもらう
   - Gmail の「フィルタとブロック中のアドレス」設定を確認
   - 受信側のドメインのバウンス（メールサーバーの拒否）有無を確認

3. **送信されていない場合**
   - 該当機能の Sentry エラーを確認（`feature: email-reminder` 等のタグ）
   - `RESEND_API_KEY` が本番環境に設定されているか確認
   - 顧客レコードに `email` が登録されているか確認

### 「迷惑メール行き」報告を受けたときの確認順序

1. **mail-tester.com にテスト送信** → スコアと改善点を確認
2. **Gmail Postmaster Tools** にドメイン登録 → 数日後にレピュテーション確認
3. **DMARC レコード確認**: `dig TXT _dmarc.salonkarte.com`
4. **テスト Gmail で実機確認**: 確認メールを別 Gmail に送って迷惑メール行きするか
5. **ヘッダー解析**: 受信メールの「ソースを表示」で `Authentication-Results` を確認
   - `spf=pass` + `dkim=pass` + `dmarc=pass` ならフィルタ起因
   - いずれか fail なら認証起因（DNS 設定問題）

### Cron 起因のトリガー（前日リマインド）が動かない場合

→ `20-cron-jobs.md` の確認手順を参照

## 既知の問題・今後の予定

### 既知の問題

| 問題 | 影響度 | 対応状況 |
|------|------|--------|
| 迷惑メール行き（Gmail）| 高 | DNS 認証は完了済み。本文・ヘッダー側の改善が未着手 |
| メール配信ログを DB に保存していない | 中 | LINE は `line_message_logs` に保存しているがメールはなし。再送・調査の追跡性が低い |
| 確認メールが 24時間で失効する案内が地味 | 低 | 期限切れ時の再送導線（「確認メールを再送する」リンク）はあるが目立たない |

### 今後の予定（実装予定 / 未実装）

| 項目 | 状態 | 優先度 |
|------|-----|-------|
| `List-Unsubscribe` ヘッダーの追加 | 未実装 | 高（迷惑メール対策） |
| メール配信ログ DB 保存（`email_message_logs` テーブル新設） | 未実装 | 中 |
| 顧客のメールアドレス未登録時の代替案内（LINE のみ通知に切替） | 未実装 | 中 |
