## 0. 最重要の問い: 「3サロン確約まで待つべきか？」

### 結論: 待つ戦略は正しい。ただし「待つ」と「何もしない」は違う。

| 判断 | 理由 |
|------|------|
| Supabase/Vercel課金は待つ ✅ | 月$45の固定費を1サロンの状態で発生させる合理性がない |
| Stripeテストモードも待つ ✅ | 決済導線はテスターの検証を妨げない現在の設計で正しい |
| **集客活動は今すぐ始める** ⚠️ | 「3サロン」は待っていても来ない。能動的に取りに行く必要がある |

### 数字で見る現実

```
現在: テスター1サロン（有料意思あり）
目標: 3サロン確約

必要なアクション:
- SEO記事 → 検索流入 → LP → サインアップ の導線構築
- SEO効果が出るまで3〜6ヶ月 → 今日始めないと遅い
- コスト: 0円（既存のブログ機能で記事を公開するだけ）
```

**結論: インフラ課金は待つ。集客活動は今すぐ始める。この2つは矛盾しない。**

### 2.0 最重要: 記事は「サロンオーナー目線」で書く（開発者目線NG）

**読者はサロンオーナー（ITリテラシー低い、スマホメイン）。** 彼女たちの知りたいこと：

- 「サロン 電子カルテ 比較」で検索する人は**もう買う気がある**→ 記事→LP→契約が最短
- 「サロン経営 大変」で検索する人は情報収集段階で、契約まで遠い
- 限られたリソースは「最も契約に近い人」に集中する

### 2.3 記事品質基準（100点の記事とは）

#### 記事構成テンプレート

```
1. リード文（150字以内）
   - 読者の悩みを代弁 → 解決策の提示 → 記事を読むメリット
   - AI検索に拾われやすい「結論ファースト」

2. 目次（自動生成）

3. 課題提起セクション
   - 読者の「あるある」を3つ具体的に描写
   - 共感 → 「このままだとこうなる」危機感

4. 解決策セクション（メイン）
   - 具体的な手順・方法を図解付きで解説
   - 自社プロダクトへの自然な言及（押し売りではなく）
   - 実体験ベースの一次情報を必ず含める

5. 比較・選択肢セクション（ボトムファネル記事の場合）
   - 公平な比較表（自社だけ持ち上げない）
   - 各ツールの向き不向きを正直に書く

6. まとめ + CTA
   - 要点3つの箇条書き
   - 「無料ではじめる」への自然な誘導
   - マイクロコピー: 初期費用0円 / クレジットカード不要

7. 著者プロフィール（E-E-AT対策）
   - 「個人サロン向けアプリ開発者」としての経歴
   - なぜこのテーマに詳しいかの根拠
```

### 3.1 紹介プログラム強化（優先度A — 実装済み）

**現状**: 紹介コード + 双方1ヶ月無料が実装済み。

**重要: 今の段階で「有料で使います」の確約は求めない。**

段階的なアプローチ:

| ステップ | やること | タイミング |
|---------|---------|----------|
| 1 | テスターに「同業の知人で試してみたい方いませんか？」と聞く | **今すぐ** |
| 2 | 新テスターに使い始めてもらう（無料） | 紹介後すぐ |
| 3 | 使用開始2週間後に感想を聞く（「一番助かった機能は？」） | 2週間後 |
| 4 | 感想をSEO記事の一次情報として使う（許可を取って） | 記事執筆時 |
| 5 | 3サロンが「無料でも使い続けたい」状態になったらStripe本番化 | 自然に |

**「有料でも使う」の確約は、使い込んでデータが蓄積された後に自然に出てくるもの。**
今は「無料で試してくれる人」を増やすフェーズ。

**紹介しやすい素材を用意する:**
- salon-karteの画面スクリーンショット1枚 + 30秒の説明文テンプレート
- 「こういうの探してる人いたら教えて」と気軽にシェアできる形

**期待効果**: CAC $150相当（業界最低水準）

### 3.2 無料ツール提供（優先度A — 新規）

> 「記事を書くのではなく、無料ツールを作れ」(2026 SaaS SEO Playbook)
> 出典: [Outgrow — 9 Calculators Every SaaS Company Should Consider](https://outgrow.co/blog/interactive-calculators-saas-companies)
> 出典: [ProjectionHub — Salon Sales Calculator](https://www.projectionhub.com/resources/salon-sales-calculator)（実在する競合ツール）

**案1: サロン売上シミュレーター（最推奨）**

```
入力:
- 1日の平均施術人数（例: 3人）
- 平均客単価（例: 8,000円）
- 月の営業日数（例: 22日）

出力:
- 月売上: 528,000円
- 年売上: 6,336,000円
- ホットペッパー利用時のコスト: 月2.5万円（売上の4.7%）
- salon-karteのコスト: 月2,980円（売上の0.6%）
- → 年間26万円の節約
```

- SEO効果: 「サロン 売上 計算」「個人サロン 年収」で検索流入
- リード獲得: 結果表示後に「この売上をもっと伸ばすには？→ 無料ではじめる」のCTA
- 工数: LP内に1つのClient Componentを追加、**4〜6時間**で作れる
- 参考: ProjectionHubが既に英語版を公開中 → 日本語版は競合なし

**案2: リピート率診断ツール**

```
入力: 月間新規数 / 月間リピート数 / 平均来店頻度
出力: リピート率 / 業界平均（80%）との比較 / 改善ポイント3つ

「あなたのリピート率は65%。業界平均は80%。
 60日以上来ていないお客様への再来店促進で改善できます」
```

- SEO効果: 「サロン リピート率 平均」「リピーター 増やし方」で流入

**案3: 確定申告 準備度チェック**

```
質問形式（5問）: 「売上の記録方法は？」「経費の管理は？」等
出力: 準備度スコア（100点中）+ 不足している項目
```

- SEO効果: 「個人サロン 確定申告」で流入
- 時期: 確定申告シーズン（1〜3月）に効果大

**メリット**: 被リンク獲得 + SEO + リード獲得を同時達成。
ツールは「使ってもらう」ことが目的なので、メールアドレス入力は不要（ゲート不要）。

### 3.3 パートナーシップ（優先度B）

**候補**:
- **サロン開業支援の行政書士・税理士**: 開業時にsalon-karteを紹介してもらう

#### 現在の課金モデル評価

**2026年のコンバージョン率ベンチマーク:**
- フリートライアル（カード不要）: **15〜25%** コンバージョン
- フリートライアル（カード必要）: **50〜60%** コンバージョン

- サロンオーナーはITリテラシーが低い → カード要求でドロップする

## 6. PDCA 運用体制（2026-03-09 追加）

### 6.1 データ収集（GA4 カスタムイベント）

集客ファネルの各段階を GA4 カスタムイベントで計測する。

| イベント名 | 発火タイミング | 計測内容 |
|-----------|-------------|---------|
| `cta_click` | LP/ブログの CTA クリック | どの CTA が効いているか（location パラメータで区別） |
| `signup_start` | /signup ページ表示 | サインアップページへの到達数 |
| `signup_complete` | アカウント作成成功 | 実際の登録完了数 |
| `onboarding_complete` | サロン初期設定完了 | 定着率 |
| `first_record` | カルテ保存成功 | アクティベーション率 |
| `blog_read` | ブログ記事スクロール 75% | 記事の質・エンゲージメント |

**実装箇所:**
- `src/lib/analytics.ts` — イベント送信ユーティリティ（型安全）
- `src/components/lp/cta-link.tsx` — CTA リンクコンポーネント
- `src/components/blog/blog-scroll-tracker.tsx` — ブログスクロール計測

### 6.2 週次レビューサイクル（毎週土曜 9:00 JST）

GitHub Actions で自動実行される週次レポートをベースに PDCA を回す。

```
毎週土曜 9:00 JST
  → GitHub Actions 起動
  → scripts/acquisition-report.ts 実行
  → GA4 Data API + Supabase DB からデータ取得
  → Markdown レポート生成（docs/reports/）
  → GitHub Issue を自動起票（ラベル: acquisition, pdca-review）
  → その Issue をベースに Claude Code と一緒にレビュー
```

**レポート内容:**
- KPI サマリー（PV、ユーザー数、サインアップ数 vs 目標）
- 集客ファネル（CTA → signup → onboarding → first_record）
- ページ別 PV ランキング
- 流入元ランキング
- プロダクト利用状況（サロン数、カルテ数、アクティブ数）
- 自動アクション提案

**ワークフロー:** `.github/workflows/weekly-acquisition-review.yml`

### 6.3 レビューの進め方

1. GitHub Issue のレポートを確認する
2. 前週のアクション実施状況を振り返る
3. 数値の変化と要因を分析する
4. 次週の具体的アクション（最大3つ）を決める
5. Issue にコメントで記録する

### 6.4 必要な GitHub Secrets 設定

| シークレット名 | 用途 | 必須 |
|-------------|------|------|
| `GA4_PROPERTY_ID` | GA4 プロパティ ID | △（なくても DB レポートは出る） |
| `GA4_CREDENTIALS_JSON` | Google サービスアカウント JSON | △（GA4 API 用） |
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase URL | △（DB メトリクス用） |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase サービスロールキー | △（DB メトリクス用） |

> GA4 は Vercel 環境変数（`NEXT_PUBLIC_GA4_ID`）に設定済み。LP のページビュー・カスタムイベント（CTA クリック等）を計測中。
> GA4 Data API（`GA4_PROPERTY_ID` + `GA4_CREDENTIALS_JSON`）を GitHub Secrets に追加すれば、週次レポートに PV/UU が自動反映される。
